# AI Support Workbench 产品需求文档（PRD）

版本：v1.0 · 状态：Draft · 最后更新：2026-08-09

> 本文件只描述 **MVP（3 周主线）** 的产品范围。所有 "明确不做" 的条目是刻意裁剪，不是遗漏。开发期间需求只能通过 `docs/` 文档评审变更，不允许口头加需求。

---

## 1. 产品概述

### 1.1 一句话定位

面向企业客服团队的 AI 工单与客服协同平台：客服提交工单后，AI 自动完成分类、摘要、优先级和情绪识别，并从企业知识库检索资料生成回复建议；回复必须经过客服人工审核后才可发送，客户可对处理结果评分。

### 1.2 产品目标

| 目标 | 衡量方式 |
|---|---|
| 降低客服团队的重复标注成本 | 工单分类、摘要、优先级、情绪由 AI 自动完成 |
| 加快首次响应 | AI 在客服介入前准备好工单摘要和回复建议 |
| 提升回复质量一致性 | 回复基于企业知识库，并强制人工审核 |
| 记录全部操作 | 状态变化、回复、审核、删除都有审计日志 |
| 可回放可追溯 | 每一步 AI 处理都有任务记录，失败可重试 |

### 1.3 非目标

- 不替代客服，AI 只做分析和建议，最终由人决策；
- 不做多租户 SaaS；
- 不做支付、短信、邮件、小程序；
- 不做复杂统计大屏。

## 2. 目标用户

| 角色 | 描述 | 使用场景 |
|---|---|---|
| customer 客户 | 提交问题、跟进工单、评价处理结果 | 遇到产品/服务问题，提交工单并等待回复 |
| agent 客服 | 查看工单、审阅 AI 建议、编辑并发送回复、关闭工单 | 日常处理客户提交的问题 |
| admin 管理员 | 管理知识库、管理用户、查看全部工单和审计日志 | 维护系统、配置 AI、排查问题 |

### 2.1 角色边界（权限矩阵）

| 能力 | customer | agent | admin |
|---|---|---|---|
| 注册 / 登录 | ✅ | ✅ | ✅ |
| 创建工单 | ✅ | ❌（客服入口走客户视角） | ❌ |
| 查看自己的工单 | ✅ | ❌ | ❌ |
| 查看 / 分配全部工单 | ❌ | ✅ | ✅ |
| AI 结构化处理（分类/摘要/优先级/情绪） | 只读结果 | 只读结果 | 只读结果 |
| 查看 AI 回复建议 | ✅ | ✅ | ✅ |
| 编辑 / 审核 / 发送回复 | ❌ | ✅ | ✅ |
| 关闭工单 | ❌ | ✅ | ✅ |
| 工单评价 | ✅（仅本人已关闭工单） | ❌ | ❌ |
| 知识库文档上传 / 删除 / 检索 | ❌ | ✅ | ✅ |
| 用户管理（查看、改角色） | ❌ | ❌ | ✅ |
| 查看审计日志 | ❌ | ❌ | ✅ |

> 设计决策：**customer 由前端注册生成，agent 与 admin 由 admin 在后台管理创建**。MVP 提供 `POST /auth/register` 但仅允许 `customer` 角色注册，`agent` / `admin` 只能由 `admin` 通过 `POST /admin/users` 创建（见 `api-design.md`）。

## 3. 用户痛点

| # | 痛点 | 产品回应 |
|---|---|---|
| P1 | 客服每天收到大量重复问题，人工标注分类和优先级耗时 | AI 自动完成分类、摘要、优先级、情绪识别 |
| P2 | 客服对不熟悉的业务要翻文档，回复慢 | RAG 检索企业知识库，生成回复建议 |
| P3 | AI 回复直接发出不可控，客户体验和合规有风险 | 强制人工审核，AI 永不直接发送 |
| P4 | 工单流转状态不清，谁处理到哪一步说不清 | 显式状态机 + 审计日志 |
| P5 | 客服人手不足，后台任务（AI 处理）拖慢接口 | Redis + RQ 异步处理，接口立即返回 |
| P6 | 客服团队变动，人工经验难沉淀 | 知识库 + 操作审计沉淀规范 |

## 4. MVP 范围

### 4.1 主线功能（必须全部完成，3 周内）

1. **用户与认证**：注册、登录、JWT、角色（customer / agent / admin）、密码 bcrypt 加密；
2. **工单**：创建（支持幂等）、列表（分页 + 筛选）、详情、更新；
3. **工单状态机**：`open → in_review → replied → closed`，并支持 `open → canceled`、`in_review → canceled`，非法转移返回清晰业务错误；
4. **AI 结构化处理**：分类、摘要、优先级、情绪（Pydantic schema 校验，异步 RQ）；
5. **知识库**：文档上传（PDF/TXT）、切片、Embedding、pgvector 检索；
6. **RAG 回复建议**：基于工单内容 + 知识库检索，生成回复建议；
7. **客服工作台**：查看工单、审阅/编辑建议、发送回复、关闭工单；
8. **客户评价**：对已关闭工单评分 + 评论；
9. **审计日志**：状态变化、回复、审核、删除均写入 `audit_logs`；
10. **工程化**：Redis + RQ、基础重试、基础幂等、pytest、GitHub Actions CI、Docker Compose。

### 4.2 延伸功能（放 "后续改进"，不在 3 周主线内）

- SSE 流式输出；
- WebSocket 实时会话；
- 复杂统计大屏（MVP 只提供简单工单数量接口）；
- 通用幂等框架（MVP 只做两处最小幂等，见 `technical-design.md`）；
- 自动发送 AI 回复（**本产品永久不做**，见 AI 规则）；
- 多租户、微服务、Kubernetes。

## 6. 页面结构

| 页面 | 路径 | 角色 | 说明 |
|---|---|---|---|
| 登录页 | `/login` | 全部 | 邮箱 + 密码 |
| 注册页 | `/register` | 全部 | 仅注册 customer |
| 我的工单 | `/` | customer | 本人工单列表 + 筛选 + 分页 |
| 工单详情 | `/tickets/:id` | 全部 | 详情、时间线、回复、评价入口 |
| 客服工作台 | `/workbench` | agent / admin | 全部工单列表 + 筛选 + 分页 |
| 工单处理页 | `/workbench/tickets/:id` | agent / admin | AI 建议、审核编辑、发送、关闭 |
| 知识库 | `/knowledge` | agent / admin | 文档上传、列表、删除 |
| 用户管理 | `/admin/users` | admin | 创建用户、改角色 |
| 审计日志 | `/admin/audit` | admin | 审计日志列表 + 筛选 + 分页 |

> 前端保持与项目一相同的轻量 Vue 3 + TS + Vite 单页结构，不引入组件库之外的额外路由/状态框架。路由守卫拦截未登录访问。

## 7. 用户完整操作流程

### 流程 A：客户提交工单 → AI 处理（可取消）

```
客户登录
  → 提交工单（标题 + 描述，携带 Idempotency-Key）
  → 工单创建成功，状态 open
  → 后台 RQ 任务：AI 分类 / 摘要 / 优先级 / 情绪
      → 写入 ai_processing_jobs（成功或失败都记录）
      → 失败则按 RQ 重试策略重试
  → 客户在"我的工单"看到状态与 AI 摘要
  → （可选）客户在 open 状态下取消工单 → canceled
```

### 流程 B：客服处理 → 客户评价（完整闭环）

```
agent/admin 打开客服工作台
  → 打开工单详情
  → 查看 AI 分类/摘要/优先级/情绪
  → （可选）点击"生成回复建议" → RAG 检索知识库 → 生成建议
  → 审阅并编辑建议内容（必须人工确认，不能直接发 AI 原文）
  → 发送回复（状态 in_review → replied，写审计）
  → 关闭工单（状态 replied → closed，写审计）
  → customer 收到已关闭工单 → 评分 + 评论 → 写 evaluations
```

### 流程 C：知识库维护（admin）

```
admin 登录
  → 进入知识库
  → 上传 PDF/TXT 文档
  → 后台切片 + Embedding + 写入 pgvector
  → 文档 ready 后可被 RAG 检索
  → 删除文档（级联删除切片和向量）
```

### 流程 D：用户管理（admin）

```
admin 登录
  → 进入用户管理
  → 创建 agent/admin 用户（指定邮箱、角色、初始密码）
  → 或修改现有用户角色
  → 每次操作写审计日志
```

## 8. AI 规则（不可逾越的约束）

1. **AI 只能生成分类结果和回复建议**，不能直接发送回复；
2. **AI 不能绕过客服人工审核**，回复必须由 agent/admin 确认后发送；
3. ChatProvider 和 EmbeddingProvider 保持接口抽象（`abstractmethod`）；
4. 模型、Base URL、API Key 只能从环境变量读取，不得硬编码；
5. 测试默认使用 Fake Provider，真实 Provider 只做手工验收；
6. 结构化输出使用 Pydantic schema 校验；
7. AI 失败必须记录错误，并支持 RQ 重试。

## 9. 验收标准（主线功能）

| 功能 | 验收标准 |
|---|---|
| 注册/登录 | 密码 bcrypt 存储；JWT 过期可配；错误密码返回 401 |
| 角色 | 3 种角色；越权访问返回 403 |
| 工单创建 | 幂等 Key 重复请求返回相同结果；非法内容 400 |
| 工单状态机 | 非法转移返回 409 业务错误；每次转移写审计；`open→canceled`、`in_review→canceled` 生效 |
| 分页筛选 | 所有列表接口支持分页；筛选条件可用 |
| AI 结构化处理 | 4 个字段由 Pydantic 校验；失败记录到 job 并重试 |
| 知识库 | PDF/TXT 上传 → ready 可检索；非法类型 400 |
| RAG 建议 | 无检索依据时明确提示；建议可编辑后发送 |
| 评价 | 仅本人已关闭工单可评价；一单一评 |
| 审计 | 状态变化/回复/审核/删除均有日志；admin 可查 |
| RQ | worker 运行在 Linux 容器；任务失败可重试 |
| 幂等 | 工单创建重复请求不产生重复工单；RQ job 不重复处理 |
| 测试/CI | pytest 全绿；GitHub Actions 自动运行 |
| Docker | 三服务 + Redis + worker 一键启动 |
